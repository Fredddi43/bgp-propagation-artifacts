## What changed from v1 (sol-h3t W1-A1/A2/A3 and sol-final D300-W1-CONTROL-1)
1. **Live enforcement (A1).** The terminal-only guards are replaced by the PATH B live budget of the shard-27 successor, applied in every stage (`live_budget_factory`, subclass of the pinned original/output budget, so original logical rules, rewrite refusal and own-scratch handling are kept): prospective file/directory counts before creating anything (waves 1024 files / 8 dirs vs observed 473 / 2; assemble and audit 64 / 8); a stat-only observed-allocation check before every new file (observed + active-write allowance <= task ceiling) and after every finished file; growth-review stop at 6 GiB logical (the V48-preserved threshold, now enforced live); writer 8 GiB and per-file caps on observed sizes; mkdir only inside the output (plus the pinned existing CAIDA cache), rename/link/symlink/truncate refused; plus a `LiveMonitor` thread polling task and wave-aggregate allocation every 0.25 s that SIGKILLs the worker on violation (reason recorded in `live-stop-NNNN.json`, supervisor records the failed terminal). The synthetic counterexample (4097 empty files) is refused at the 1024th file (test).
2. **Allocation model, stated plainly.** The dense 1.25 x logical model is NOT used: one task under it needs ~13 GiB, more than the whole `timing_live_build_wave` row (11.02 GiB), so no concurrency can be funded by that row under it. The packets use `measured_density_live_v1`: allocation is observed live and one active write is bounded by 0.15 x the 2 GiB file cap + 1 MiB = 323,171,124 B (measured density of files >= 64 MiB <= 0.0914, >= 256 MiB <= 0.0418, small-file block slack <= 4,425 B; census of 69,841 files). This is a substantive modeling decision that needs root's explicit decision and independent acceptance; it is carried in the plan, the binding exception and the scoped phase exception.
