### SUPERSEDED 2026-10-28 by q33 (deadline 2026-10-28T15:00Z): origin launches as ONE wave
The serial order above costs ~13 h of dead schedule (invalid ~1 h → canary ~6.6 h → valid-rest ~6.6 h) while the 20 valid arms are the critical path and the cpu partition is heavily allocated by other users — a 64-CPU request waits for a whole free slot, and the batch-1 forward pass barely uses extra cpus (q30 ESTIMATES option 5). New flow (RESOURCE-POLICY ADDENDUM "headroom, not maximum"): submit the canonical 40-arm spec as a SINGLE array — `--array=0-39%40` at `--cpus-per-task=8 --mem=900000M --time=1-00:00:00` (invalid arms' own plan shape is 4 cpus / 400000 MiB; inside the mixed array `g2_exec` re-binds them up to the live allocation, g2_exec.py:82-83). The scheduler decides the order. The CANARY IS REPLACED BY A MONITORING RULE: the root/driver watches the first valid arms' `sacct MaxRSS` + per-event seconds (predictions `forward_seconds`; the invalid receipts give the early signal); ONLY if a valid arm dies OOM (or MaxRSS > ~85% of 900000 MiB) rerun that arm — and only that arm — at `--mem-mib 1000000` (fresh attempt; arms stay one-attempt). Do not preempt slow-but-alive arms: q30's worst case (15.6 h, NFS contention priced in) fits the 24 h wall; the NFS read analysis (README "Origin G2 order") puts the 20-valid-arm aggregate at ~320 MB/s cold with verify re-hashes served from the 900 GB page cache — a slowdown, not a wall-clock killer. `check_plan` now refuses origin plans BELOW the per-cohort shape (valid < 8/900000, invalid < 4/400000) and keeps refusing sub-16x bounds. The three-wave generator is kept as an option (`make_g2_plan.py --waves`, per-cohort shapes invalid 4c/400G, canary+valid-rest 8c/900G) for the case where root cancels the single-wave decision; until then this section's numbered order above is NOT executed.
